# skd更新通知

2026-09-10のユーザー指定。ad・noticeの機能追加は今回の対象外。

- 通知先は旧スケジュール通知のトークを引き継ぐ。登録先IDは専用privateデータrepoに保存する。
- ワークフローが重なっても同じ更新を二重通知しない。
- 最初に検知通知を送り、更新種類は同じ投稿へ追記する。
- Botが更新対象のTSVを取得し、KBC-rakv0-eventのパーサーで解析する。
- 更新前のrawにある種類別の最新TSVと、今回のTSVを同じパーサーで解析し、追加されたイベントをgatya、sale、item、missionに分け、この順で送る。
- 各種類は独立したコードブロックにし、各最大5件。残りは「その他〇件」と表示する。
- 開催日時・バージョンだけ差し替わった予定は追加分から外し、追加分の後の「変更」コードブロックへ4種類まとめて表示する。種類名と変更前→変更後を示し、合計最大5件、残りは「その他〇件」と表示する。元の予定が残ったまま別の予定が増えた場合は追加分とする。
- 一覧の名前・日時・ガチャフラグ・開催期間・数量はo.gatya / o.sale / o.itemに準じる。missionはsaleのミッション分類・名前解決を使う。
- skd通知とo.gatya / o.sale / o.itemの一覧から🟠を削除する。開催中の🟢は維持する。
- missionは原文の改行と`<br>`をコードブロック内の改行として表示する。複数行でも1ミッションを1件と数える。
- 追加がない種類のコードブロックは省く。追加がある種類はgatya、sale、item、missionの順を保ち、変更がない場合は「変更」欄も省く。終了済みは除外する。更新通知とo.skdでは常設の追加・変更も表示対象にし、終了日2030/01/01は「常設」と表示する。301・302はitemに表示する。
- 追加分と変更欄の送信完了後、旧スケジュール通知と同じKBC履歴リンクを送って終了する。
- 送信結果が不明な投稿を自動で再投稿しない方針を、種類別の追加通知にも適用する。

## o.skd

- 引数なしは最新の更新、`o.skd 2026/07/30`または`o.skd 2026 07 30`は日本時間で最も近い更新日の内容を返す。
- 最初のTSV保存時刻から100秒以内にあるTSVを同じ更新としてまとめる。同じ種類が複数あれば最後のTSVを採用し、比較元はその更新の開始より前に保存された直前のTSVとする。
- 同じ日に複数の更新があれば最後の更新を選ぶ。前後の日が同じ距離なら過去側を選ぶ。
- 「スケジュール更新」、時刻、更新種類に続けて、通知と同じ追加・変更分とKBCリンクを返す。件数上限、空の種類の省略、改行は通知と共通。
- raw履歴だけでは過去の検知時刻を確定できないため、時刻は最初のTSV保存時刻を使い、返信に「TSV保存時刻」と明記する。比較元のない最初の保存分は、その旨を示して保存内容を追加分として扱う。
- 過去分の開催中・終了済み判定は選んだ更新時刻を基準にする。存在しない日付・余分な引数は使い方を返し、外部取得失敗はエラーを返す。
- コマンドを実行したチャンネルだけへ返信する。通知先の登録や配送履歴を書き換えない。サイトURLの静的返信は`o.skdsite`で利用できる。

健康維持メンテナーの設定コマンドは引き続き別作業。[保存要件](storage.md)に従う。
